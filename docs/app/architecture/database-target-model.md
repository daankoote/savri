## Model Boundaries

- Gate 1 local proof on 2026-07-20 created and proved a local schema foundation for:
  - `app_connections`
  - `app_connection_periods`
  - `app_connection_ownership_periods`
- Gate 1 proof status is `PARTIAL PROVEN / LOCAL SCHEMA ONLY`. It proves local tables, constraints, RLS, grants, guards, history/supersede behavior, and cleanup. It does not prove CAR access, network-operator registry truth, REV input compatibility, customer-facing writes, operations workflow, remote deployment, or legal acceptance of any EAN claim.
- Gate 1 connection write boundary proof on 2026-07-20 added local service-role-only RPCs for declaring connections, declaring ownership claims, deciding ownership claims, and supersede-history corrections:
  - `app_declare_connection_v1`
  - `app_declare_connection_ownership_v1`
  - `app_decide_connection_ownership_v1`
  - `app_supersede_connection_ownership_v1`
- Gate 1 write boundary status is `CURRENT PROVEN / LOCAL RPC ONLY`. It proves security-definer RPCs, safe `search_path`, service-role-only execute grants, scoped idempotency, minimized audit events, scope validation, state transitions, supersede-history creation, and cleanup. It does not prove CAR access, customer-facing endpoint behavior, operations review UX, external ownership verification, REV compatibility, remote deployment, or production compliance.
- `app_connection_periods` is a Gate 1 split from the earlier target-table idea that placed period fields directly on `app_connections`. The split is intentional for local proof: stable EAN identity is separated from time-bound location/network-operator/configuration facts.
- Local EAN validation is syntactic only: exactly 18 numeric digits. The schema does not prove checksum, registry existence, CAR availability, or aangeslotene truth.
- Secondary allocation point / MLOEA constructs are represented as declared/reviewable facts only. They are not automatically eligible, accepted, or bookable.
- `app_cases` replaces the broad all-purpose meaning currently carried by `app_customer_dossiers`; domain-specific state moves to mandate, EAN, evidence, kWh, review, batch, REV, verification, CAPA, and finance tables.
- Evidence transport remains separate from evidence acceptance: `app_evidence_files` and `app_evidence_versions` prove bytes and versions; `app_evidence_decisions` proves acceptance or rejection.
- `app_internal_support_controls` is separate from `app_verification_location_visits`. Internal selection may be `manual`, `random`, `risk_based`, or `verifier_request`, but its result can only be `approved`, `rejected`, `follow_up_required`, or `inconclusive` within the internal support scope. It may never set `officially_verified`, `verification_statement_issued`, `materiality_accepted`, or `REV verification result registered`.
- kWh raw imports, normalized readings, transformations, exclusions, and booking items are separate so raw truth, derived truth, and decisions do not overwrite each other.
- Finance uses append-only ledger entries and reversing entries; customer entitlement is a projection, not the ledger.
- The electricity TKV source is mapped. Verification target tables now separate ENVAL support data from external professional truth: ENVAL may prepare scopes, populations, evidence packs, schedules, responses and safe projections; verifier-authored risk, sample, plan, finding and statement outcomes retain immutable external provenance.
- The `2%` materiality value may appear only in verifier plan/result context. It is forbidden as an automatic evidence-acceptance, eligibility, dossier, booking or statement threshold.
- `app_verification_statements` records an externally issued or not-issued outcome. No ENVAL writer may create an official statement or advance a batch to verified without authenticated external provenance.
- TKV 3.0.5 applies a minimum verification-retention class to verification data/documentation. Other customer and operational categories remain purpose-, legal-basis- and category-specific.

## External Integration Persistence And Extensibility

Stable customer, representation, location, connection, charger, charge-point, meter/MID, mandate, evidence, kWh, review, support-control, correction, booking, and audit entities form the provider-independent core.

External integration data is separated into four entity classes:

| class | target representation | rule |
|---|---|---|
| external reference | `app_external_references` | Identifies an external object/result and its validity/provenance without copying provider response fields into core tables. |
| observation | `app_extracted_observations` plus domain-linked external references | Immutable observed data; never automatic core truth or decision. |
| import | `app_kwh_raw_imports` and other future capability-specific immutable raw-import records | Preserves raw payload/evidence reference and content hash before normalization. |
| provenance/transformation | `app_kwh_transformation_runs`, audit events, and transformation links on external references | Reconstructs adapter/mapping/method version, input hash, output hash, actor/request and decision lineage. |

Every external capability must expose a provider-independent port with zero or more adapters and a manual fallback where allowed. Its persisted contract includes raw response/evidence reference, source system, external reference, retrieval time, valid-from/valid-to, payload/content hash, transformation provenance, internal review status, decision reference, and failure/retry state.

Provider responses do not mutate core truth directly. External references, observations, imports and transformations are immutable/versioned and may be superseded without losing history. Core tables contain no provider-specific response fields. Adding CAR, EAN/aangeslotene, DSO, KvK, MID/certificate, CPO/backoffice, energy-supplier, kWh export, REV, verifier, payment, or another provider normally requires only a new adapter, mapping and contract tests; no destructive core migration should be required.
