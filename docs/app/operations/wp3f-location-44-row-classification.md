## Privacy Boundary

The analysis ran inside an explicit local read-only transaction. Raw rows were
used only inside the database query. No customer, dossier, location, charger,
document, connection or provider UUID; address component; coordinate; name;
email address; telephone number; dossier number; file name; storage path; or
document content was printed, copied, written to this file, or stored in Git.
The ephemeral alias-to-ID mapping was rolled back and was not persisted.

`provider_observation_present` is only a boolean derived from the presence of a
provider label, provider identifier, or non-empty lookup metadata. It does not
establish provider authority, freshness, physical-site identity, or accepted
truth.

## Classification Rules

- `ONE_TO_ONE_CANDIDATE` would mean only that one current snapshot could
  possibly map to one new root plus one initial observation. It would not
  authorize an accepted version or migration.
- A normalized key uses only already-normalized postcode, house number, suffix,
  and country inside the read-only query. A match supports
  `POSSIBLE_DUPLICATE` only and never a merge.
- `CONFLICTING` means that the same normalized-key cluster contains more than
  one distinct non-empty provider identifier. No identifier is exposed.
- Every row requires manual review because a current snapshot, provider
  observation, or normalized-address match does not prove physical-site
  continuity.
- `automatic_promotion_allowed` is `NO` for all 44 rows.
